# Runbook

How Sales Ops is deployed and operated. Nothing here runs on its own: every
dashboard action, deploy and database write outside a laptop needs Javier's OK.

## Topology (Render Blueprint, `render.yaml`)

| piece | what |
|---|---|
| `sales-ops` (web, Python) | builds `web/dist`, runs `flask db upgrade`, serves the API and the SPA with gunicorn |
| `sales-ops-worker` (worker, Python) | `python -m app.worker`: parse shows, AI supervision; polls the `jobs` table |
| `whatnot-ops-db` (Postgres, basic-256mb) | the only state (name kept: renaming would create an empty database) |

The web service never runs jobs in production (`JOBS_INLINE` must stay
unset); the worker does. Both read the same `DATABASE_URL`.

## First deploy

1. Render → New → Blueprint → this repo, branch `main`. Render creates the
   database and both services and applies migrations on start.
2. Add `MAILGUN_API_KEY`, `MAILGUN_DOMAIN`, `EMAIL_FROM` on **both**
   services: the web service sends invites, the worker sends password-reset
   emails (`reset_mail` job). Add `APP_URL` on the web service once a domain
   is attached. Without Mailgun the web service only logs invites, and a
   reset job fails with "MAILGUN_API_KEY / MAILGUN_DOMAIN unset here" in the
   worker log.
3. Optional AI: `AI_PROVIDER=claude` + `ANTHROPIC_API_KEY` (or `jev` +
   `JEV_API_KEY`, `JEV_API_URL`) on **both** services. The worker makes the
   calls. `AI_PROVIDER=fake` is refused in production.
   Optional Whatnot Seller API (`docs/WHATNOT_API.md`): `WHATNOT_API_TOKEN` and
   `WHATNOT_WEBHOOK_SECRET` on **both** services (the worker reads Whatnot and
   applies orders; the web service receives the webhooks and prints labels).
   There is no sandbox: the token is the live shop. Register the webhook
   address in Seller Hub only after the deploy that serves it is live, and
   the owner has pressed Connect in Settings. `WHATNOT_API=fake` is refused
   in production.
4. Smoke test (also `make smoke BASE_URL=https://…`):
   `GET /api/health` → `{"status":"ok","db":true}`; `/` serves the sign-in
   page; `/some/route` falls back to the SPA; `/api/nope` is 404.
5. Admin: set `ADMIN_EMAIL` on the web service **before** anyone visits.
6. Client address (per-address rate limits): open the portal once, then find
   the web log line `client address check: using <ip>, Cloudflare saw <ip>
   (match …)`. `match` means `PROXY_HOPS` (default 2: Cloudflare, then
   Render) is right. On `MISMATCH`, compare the first address with what
   https://ifconfig.me says for your own connection: if the app is using an
   edge or private address, set `PROXY_HOPS` one higher; if it is using a
   value you can set yourself (send `X-Forwarded-For: 203.0.113.9` with curl
   and see it echoed), set it one lower. Redeploy, and check the line again.
   Only that email can create the shop on `/signup`, once, and it must type
   the one-time **setup code** (`SETUP_TOKEN`, generated by the Blueprint:
   Render → web service → Environment). Without both, production never
   opens sign-up. Also check Database → Networking shows no public access
   (`ipAllowList: []`). That account is always an owner (the app
   refuses to demote or disable it; logging in restores it). To hand the shop
   over, invite the new person, then change `ADMIN_EMAIL` to their email.
   Fallback from the web service's Shell:
   `cd api && flask --app wsgi.py users create-owner --org "Shop" --email you@… --name "You"`.
   **Support account** (optional): set `IT_SUPPORT` (email) and
   `IT_SUPPORT_PASSWORD` (10+ characters) on the web service. The start
   command's `flask ensure-support` and the shop's sign-up create or repair that
   account as an owner of the shop: it cannot be demoted or disabled from Team,
   logging in restores it, and a changed `IT_SUPPORT_PASSWORD` takes effect at
   the next deploy. Set both or neither; a weak password fails the deploy.
6. Settings → set the shop's Whatnot username (host). Then **Laptops**:
   download the extension (the zip already points at this portal), load it
   unpacked, and **Connect a laptop** → type the 8-character code in the
   extension's Settings. One code, one laptop, 10 minutes.

## Day to day

- **A show is live**: the extension uploads every few seconds; the worker
  parses within ~3 s of each batch; the dashboard's live pill links to it.
- **Review queue** (owners/managers): unknown items, stock conflicts,
  ambiguous cancellations, AI proposals. Assigning a SKU with "remember" teaches
  the parser the chat name.
- **After the show**: Seller Hub → export orders → Payments tab on the show →
  Preview → Apply. Paid rows take the stock; refunded rows release it.
  Orders → To fulfil → Pick list → pick / pack / ship.
- **Reports**: one show or a date range as `.xlsx`.

## Operations

- **Logs**: web and worker logs in Render. The worker logs each failed job
  with its attempt; after 5 attempts a job is `failed` in the `jobs` table.
  Re-queue by setting `status='queued'` (needs Javier's OK on prod).
- **Re-parse a show**: show page → Parse now (re-evaluates only lines that led
  nowhere; existing sales are never rewritten).
- **AI evaluation**: `flask --app wsgi.py ai-eval` replays the synthetic
  corpus through the configured provider.
- **Backups**: Render Postgres daily backups (paid plan). Restore = new
  database from a backup, repoint `DATABASE_URL`, redeploy.
- **Secrets**: only in Render env vars. A leaked key is rotated, never just
  removed from history. `SECRET_KEY` rotation signs everyone out.
- **Billing**: a suspended workspace shows up as failed deploys and 502s;
  check billing before debugging.

## Migrations

`flask db migrate` prints the generated file — rename *that* file to the
next `NNNN_name.py`. A revision that has run on prod is frozen; new changes
are new revisions. Downgrades that drop tables using Postgres enums must drop
the enum types (see 0004, 0007).

A deploy runs every revision the database has not seen. `flask db current` on the
service (or the deploy log's "Running upgrade" lines) says where it stands;
`flask db heads` must print one head before a merge. Two downgrades refuse on
purpose once they hold data that moved stock: 0033 (`sale_items`) and 0035
(`giveaway_items`).

## Extension for the team

The web service's build also builds `extension/dist`, and **Settings →
Laptops → Download** serves it as `chat-scraper-<version>.zip` with this
portal's address (`APP_URL`, else `RENDER_EXTERNAL_URL`) written into
`defaults.json`. Each laptop then connects with a pairing code; nobody copies
keys. Bump `extension/manifest.json`'s version when the extension changes so
the team can tell which build they have. Without Render:

```bash
cd extension && DEFAULT_SERVER_URL=https://ops.example.com npm run package
```

Later: an unlisted Chrome Web Store listing gives install-by-link and
auto-updates (one-time developer registration and Google's review).

## Whatnot connection

- **"The Whatnot connection stopped working" on every page**: Whatnot answered
  401 or 403. The account owner makes a new token in Seller Hub (or adds the
  missing permission); put it in `WHATNOT_API_TOKEN` on both services. Settings →
  Whatnot → Check now clears the banner once a call works.
- **Read now**: Settings → Whatnot → Check now also reads Whatnot's shows and a
  live show's orders at once, without waiting for the next sweep.
- **Nothing arrives during a show**: Settings → Whatnot shows the last update
  received. With no webhook for 10 minutes while a show is live, the worker
  reads the show's orders itself every sweep (5 min). A failing webhook address
  is throttled and then removed by Whatnot: add it again in Seller Hub.
- **A read failed**: the `jobs` table keeps the error line (`kind` starting
  `whatnot_`); `whatnot_sync_state.last_error` says which reading. Reads never
  change a sale, a payment or stock; they are safe to run again
  (show page → Payments → "Read again from Whatnot").
- **Freeze merges while a show is live**, as before: a deploy restarts the web
  service, and Whatnot retries a webhook it could not deliver (for 2.5 days),
  but a migration mid-show is still a risk not worth taking.
